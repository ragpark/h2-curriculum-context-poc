What is this for?

Imagine a supply teacher walking into your classroom. They know their maths. But they don't know your pupils. They don't know who keeps getting the same thing wrong, how you explained it last week, or what you haven't taught yet.

An AI tutor is in the same position. It is clever, but it walks in cold every time.

This prototype tests one idea for fixing that: give the tutor a set of class notes before it helps a pupil. To make those notes useful, everything is organised around one shared curriculum map. The map is a list of the topics in the subject, showing what comes before what and the mistakes pupils often make.

The big question: does a tutor give better help when its notes are organised around the curriculum map, compared with a pile of the pupil's answers and some worksheets? The Evaluate page tests exactly that.

Start here: a 5-minute tour

  1. Go to Overview and press “Run the whole demo”. This fills the prototype with the made-up class's worksheets and the pupils' answers. It takes a few seconds.
  2. Open “Curriculum map”. Each box is a topic. Lines show which topics you need first. Click a box to see common mistakes for that topic and how it can be taught.
  3. Open “Teacher's materials”. Click a worksheet to open it. Under each part you will see coloured labels. The computer added these by reading the worksheet: which topic it teaches, which method it uses, and which mistakes it tackles.
  4. Open “Pupil progress” and choose Amara. The map now shows what she can do (green) and where she is stuck (red). She keeps making the same sign mistake.
  5. Open “Tutor briefing”. Press “Assemble & ask tutor”. On the left is what a tutor gets from a pile of Amara's answers. On the right is the same information organised by the map. Compare the two.
  6. Open “Evaluate”. This shows how well the prototype did when tested. See “How to read the test results” below.

The second subject: English, Macbeth

Maths was the easy case: topics come in a clear order, like rungs on a ladder. English literature is not like that. Lady Macbeth, ambition and blood imagery are not steps; they are all connected to each other, and a pupil can meet them in any order. So we built a second map to test whether the idea still works. Use the Subject box at the top of the page to switch.

How the English map is different

  • Five groups instead of a ladder: the play's background (context), characters, themes, language and form, and writing skills.
  • “Related” links instead of “you need this first”. Click a topic and dotted lines show what it connects to. Only the writing skills build on each other: you need to pick good quotations before you can analyse them.
  • Key quotations are on the map, each linked to the characters and themes it shows.
  • The acts of the play are on the map. In English, “has this been taught?” is mostly about how far through the play the class has read. Lady Macbeth is taught in week 2, but her sleepwalking scene is in Act 5, which the class reaches in week 6.
  • Pupil evidence is marked written work, not right-or-wrong answers: the task, the topics it covered, the mark, and the mistake the teacher noticed, if any.

A mistake about a writing skill, such as retelling the story, matters whatever the question is about. So the tutor briefing mentions it even when the pupil asks about a character or a quotation.

Testing a different tutor against the map

The tutor built into this prototype is a stand-in. It exists so the tests can run; it is not a product. The real question for a school or a vendor is: would our tutor give better help if it had the map's notes? You can answer that here without changing the map, the pupils or the tests.

Because the marking is the same, every tutor gets three scores out of 15: with no notes, with a pile of raw records, and with the map's briefing. The gap between the last two is what the map is worth to that tutor.

Two ways to plug a tutor in

  1. Live (webhook). Give the prototype a web address. For each test question it sends the tutor a small package: the pupil's message, which of the three kinds of notes this turn uses, and the notes themselves. The tutor sends back its reply. The prototype marks it. Use “Test connection” on the Evaluate page to check the wiring before a full run.
  2. Offline (file exchange). If the tutor can't be reached over the web, download the full set of test turns as a file (every question, three times over, each with its notes), run the tutor on them wherever it lives, and upload a file of its replies. The prototype marks those exactly as it would live replies.

How to do it

  1. Open Evaluate and scroll to “Independent tutors on the same test”.
  2. Register the tutor: give it a name, choose live or offline, and for live paste the web address (and a shared secret if you want the tutor to check that requests really come from here).
  3. Pick the tutor in the drop-down next to Run, choose a test set, and run it (or, for offline, download the turns, then upload the replies).
  4. Read the result the same way as for the built-in tutor (see “How to read the test results”). The comparison table above the registration form lines up every tutor that has been run on the same set.

What the tutor receives

For a “map” turn, the notes are the same briefing you can see on the Tutor briefing page: the topic to focus on, what the pupil can and can't do yet, the mistake pattern to address, what the class has covered, the teacher's method, and a suggested next step. For a “raw records” turn, it gets the pupil's last few results and some worksheets found by keyword. For a “no notes” turn, it gets only the pupil's name. The tutor may ignore any of it; the marking will show whether that was wise.

Three cautions

  • Compare a tutor with itself first. “With map” versus “with raw records” for the same tutor is the fair test. Comparing two different tutors is shakier, because the model answers were written with one teaching style in mind, and a tutor with a different style can lose marks for reasons that have nothing to do with the map.
  • The briefing's wording was tuned on the built-in tutor. Another tutor may read it differently. If a tutor scores badly in the “organised by the map” version, look at what it did with the notes before concluding the map didn't help.
  • Only synthetic data leaves the prototype. Everything sent to a tutor is about fictional pupils. If you ever connect this to real classroom data, that changes, and the tutor's data handling becomes part of the assessment.

Technical detail, the exact message formats and the reasoning behind the design are on the Theory and Connect a tutor pages.

Agreed adjustments: what a teacher requires the tutor to do for one pupil

A class is never one pupil. Some are working well below the rest, some well ahead, and some have needs that a good teacher already knows about and plans for. The map can tell the tutor where a pupil is. It cannot and should not guess why. That is what this part is for.

It is the prototype's version of the thing a SENCO writes and a class teacher reads: how this pupil learns best, what helps, what to avoid. It is written by a person, confirmed with their name and a review date, and sent to the tutor as instructions it must follow.

Three rules

  • Never guessed. Nothing here is worked out from a pupil's answers or how they behave. A teacher chooses it. (The “Learning behaviour” panel is different: that is worked out from answers, and it is only advice.)
  • Instructions, not labels. The choices are things like “one step at a time”, “no hint before an attempt”, “may work beyond the class scheme”. There is no box for a diagnosis or a need type, on purpose. The tutor is told what to do, not what the pupil “is”.
  • Required, and dated. In the briefing they appear as required, next to the advisory notes, and the two are never mixed. Each set has a review date; after it, the adjustments stop being sent until someone re-confirms them, which is how provision works in a school.

Try it

  1. Open Pupil progress and choose Ben. His “Agreed adjustments” panel shows six, confirmed by his teacher with the SENCO.
  2. Open Tutor briefing for Ben and press “Assemble & ask tutor”. In the map's briefing, look for the blue-edged “Agreed adjustments (required)” block. The raw-records version gets the same adjustments, but as a teacher's note in the pile.
  3. Now do the same for Bilal, who gave exactly the same answers and has no adjustments. Compare the two replies.
  4. Do the same with Farah (may work ahead of the class) and her twin Fatima.

The test

On the Evaluate page, the “Agreed adjustments” set asks each pair the same questions and adds a sixth mark: did the reply honour the agreed adjustments, and for a twin with none, did it avoid inventing any? Because each pair has identical answers, the difference between twins is the adjustments and nothing else.

What this is not. It is not a way of identifying pupils with special educational needs, and it holds nothing about why a pupil has adjustments. In a real school the source would be the pupil's one-page profile or passport, and a person would still confirm each instruction before it reached a tutor. It also does nothing about the medium: a pupil who cannot read the reply needs read-aloud or symbols, which are features of the platform, not of the notes.

How to read the test results (Evaluate page)

The tutor test

We gave the same AI tutor the same pupil question three times, each time with different notes:

  1. No classroom context: the tutor knows nothing about the pupil or class.
  2. Raw classroom data: the tutor gets a pile of the pupil's recent answers and any worksheets that share words with the question.
  3. Organised by the map: the same information, sorted using the curriculum map, plus clear advice on what to focus on.

Another AI then marked each reply without knowing which notes the tutor had. It gave up to 3 marks for each of five things, so up to 15 in total:

DiagnosisDid it spot what this pupil actually needs?
Teacher's methodDid it explain things the way the class teacher does?
Respects what's been taughtDid it avoid jumping ahead to topics the class hasn't done yet?
Next stepWas the suggested next step right for this pupil?
True to pupil & classWas everything it said about the pupil and class actually true?

The exact instructions given to the tutor and to the marker are in How the test is run. The learning-behaviour test adds a sixth: did it respond to how this pupil learns? For example, did it ask Isla to have a go before giving a hint?

Three things to keep in mind:
  • Small differences don't mean much. If you run the same test twice, scores move by about 1 mark. Only pay attention to differences bigger than that.
  • “Unseen” questions matter most. We improved the prototype using one set of test questions. Doing well on those is a bit like marking a pupil on the questions they revised from. So we also wrote an unseen set before making any changes, locked it away, and only checked it afterwards, like an exam paper the candidate hasn't seen. Trust the unseen results most.
  • The marker is an AI, not a teacher. It sometimes gets things wrong. Treat its marks as a useful first look, not a final verdict.

The labelling test

We labelled some worksheets by hand, then checked how often the computer agreed. “Concept tags correct: 93%” means that out of every 100 topic labels the computer added, about 93 were right. “Expected concepts found: 100%” means it didn't miss any of the topics we expected. Again, the Unseen sets are the fairest test, because those worksheets were written and locked away before the labelling was improved, so nothing could have been tuned to pass them.

What the results say so far

Any classroom information makes the tutor's help much better: scores roughly double. Organising that information with the map helps a bit more, most clearly in getting the tutor to teach the way the class teacher does. A map that picks the wrong focus makes the help worse, so getting the map right matters.

How the test is run, and the exact instructions used

Two AI programs take part in the tutor test, and they never talk to each other. One is the tutor, which writes a reply to the pupil. The other is the marker, which scores that reply against an answer key. This section shows what each one is told, word for word, so you can judge the test for yourself.

What happens for one test question

  1. The prototype builds three versions of the notes for the same pupil and the same message: none, a pile of raw records, and the map's briefing.
  2. The tutor is given each version in turn, with exactly the same instructions each time, and writes three replies.
  3. Each reply is sent to the marker twice, separately, so a single odd judgement doesn't decide the result. The two sets of marks are averaged.
  4. The five marks (0 to 3 each) are added up to give a score out of 15 for each version of the notes.

A ten-question test therefore involves 30 tutor replies and 60 markings, which is why it takes a few minutes to run.

What the tutor is told

The tutor's instructions never change. Only the notes attached to them do. This is what it receives every time (with “maths” swapped for “English Literature … studying Macbeth” for the English pupils):

You are an AI maths tutor working one-to-one with a Year 10 pupil in an English secondary school.
You are given a CONTEXT object assembled by the school's platform. Use it to personalise your reply.
Reply in under 140 words, British English, one small step at a time, and end with a single question for the pupil.
Do not mention the context object, IDs or the platform.

After that come the notes (as the structured text you can see under “Raw context JSON” on the Tutor briefing page) and then the pupil's message. The tutor is deliberately plain. It has no personality, no memory of earlier turns and no tricks, so that the only thing that can make one reply better than another is the notes.

What the marker is told

The marker is told to be “a strict, fair assessor of tutoring”. It is given the reply, the pupil's message, and an answer key that was written by hand for that question: what the pupil actually needs, what a good next step would be, and for the class, the teacher's method, what to avoid, what has been taught and what hasn't. The marker is told the tutor may not have had this answer key. It is not shown the notes the tutor received, so it cannot give credit for matching the briefing unless the reply actually says the right thing. Its marking scheme, word for word:

Where the questions and answer keys come from

Every test question was written by hand: the pupil, their message, what they actually need, and a good next step, plus a description of each class. They are kept in plain text files alongside the prototype, under version control, so the exact wording that produced any result can always be found. The unseen sets were written and locked before the change they test, and the record shows the date. The tutor's and marker's instructions are also fixed text kept with the prototype; they were written once and have not changed since the first results.

The labelling test

This one has no AI marker. Each test worksheet has a hand-written answer key (the topics it should be labelled with, the teaching method, any misconception it mentions). The prototype's labels are compared against the key mechanically: how many labels were right, how many expected topics were found, and whether off-topic worksheets were correctly left unlabelled.

Why this matters for anyone judging the results. The marking scheme above is where the prototype's idea of “good tutoring” is written down. If you would score “method” or “scope” differently, that table is the place to disagree, and the Evaluate page's numbers should be read with your disagreement in mind. Changing the scheme would make earlier results incomparable, which is why it has been kept fixed.

What this can't tell you

  • Whether real pupils learn more. Everyone here is made up.
  • Whether teachers would agree with the marks. The marking was done by an AI.
  • Whether it works beyond one maths topic. Only solving equations has been mapped so far.
  • How it behaves with lots of messy, real data. Each made-up pupil has only a handful of tidy answers. Real schools have far more, from many different apps, and that is where the map may matter most.

Glossary

AI tutor
A computer program that chats with a pupil to help them learn, a bit like a teaching assistant.
Curriculum map
One shared list of the topics in a subject, showing which topics come first, the mistakes pupils often make and ways to teach each one. It's the same for every school.
Topic (concept)
One thing pupils learn, such as “solve equations with x on both sides”.
Builds on / comes before
A topic you need first. You need two-step equations before equations with x on both sides.
CASE
A published standard (from 1EdTech) for sharing lists of curriculum topics between computer systems. Each topic gets a permanent code and a web address, so different organisations can point at the same topic and say how their topics match up. The prototype can export its maps in this form.
Misconception
A common mistaken idea, such as forgetting to change the sign when moving a number across the equals sign.
Teaching method
A way of teaching a topic, such as the balance method or “change side, change sign”.
Representation
A picture or model used to explain, such as a bar model or algebra tiles.
Classroom context
The facts about one class and one pupil: what they answered, what the teacher taught and when, and the teacher's own worksheets. Different in every school.
Raw classroom data
Classroom context handed over as a pile, without sorting it.
Tag / tagging
A label that links a worksheet or an answer to a place on the map, like putting the right postcode on a letter.
Tagger
The part of the prototype that reads text and adds tags. There are two: a simple one that looks for key words, and a cleverer one that uses AI.
How sure (confidence)
A number from 0 to 1 showing how sure the computer is about a label. Higher means more sure.
Needs checking
A label the computer wasn't sure about, shown with a dashed outline so a person can check it.
Tutor briefing
The notes a tutor is given before it helps a pupil with one question.
Learning edge
The earliest topic the class has been taught that this pupil hasn't got yet. The best place to help next.
Secure / Developing / Gap
Can do it / getting there / struggling. Worked out from the pupil's answers.
Probably fine
We haven't seen the pupil do this directly, but they can do harder things that build on it.
Taught so far / Not yet taught
What this class has covered by this week, and what's coming later, taken from the dates on the teacher's materials.
Learning behaviour
How a pupil goes about learning: whether they plan, check their work, keep going, ask for help sensibly and know how sure to be. It's about how they learn, not what they know.
Pattern to support / Strength
An unhelpful or helpful habit we have seen a few times recently. Never a fixed label for the pupil.
Session only
Information that is used while the pupil is working and then thrown away, such as signs of frustration. It is never saved.
Teacher confirmed
A pattern a teacher has checked and agrees with. Only these would ever be shared beyond the tutor.
Scenario
A made-up pupil question used for testing, such as “I got it wrong again”.
Practice / Development questions
Questions that were used while improving the prototype. Scores on these flatter it, like marking a pupil on the questions they revised from.
Version of the notes (an “arm”)
In the tutor test the same pupil asks the same question three times, and each time the tutor is given a different set of notes: none, a pile of raw records, or the map's briefing. Each of those is one version, or “condition”. Researchers borrow the word “arm” from medical trials, where a study has a treatment arm and a control arm. The gap between the “map” version and the “raw records” version is the number the whole prototype exists to measure.
Unseen questions
Questions written and locked away before the prototype was changed, like an exam paper the candidate hasn't seen. Nothing could have been tuned to pass them, so these are the fair scores. (Researchers call this a “held-out” set.)
AI marker
A second AI that marks the tutor's replies against notes written in advance, without knowing which version of the tutor wrote them.
Map version
The map gets updated from time to time, like a new edition of a textbook. Old answers still count after an update.
Links to other curricula
How a topic on the map matches up with, for example, the GCSE subject content.
Made up (synthetic)
Invented for testing. No real pupils, classes or teachers are involved.
H1, H2, H3
Programme shorthand. H2 is the curriculum map, H1 is pupil progress, H3 is teachers' materials.
Theory

Design basis: architecture, data, evaluation, alternatives and references

The technical companion to the Help page. It describes what the prototype actually implements, on what basis, and what else could have been built. Where a design choice rests on published work, the reference is given; where it rests on a judgement made for this prototype, that is said. Everything described is in the repository and can be checked against the code.

On this page 1. The claim under test 2. Component architecture 3. The map as an ontology 4. Alignment (tagging) 5. Learner model 6. Learning-behaviour layer 7. Context assembly 8. Synthetic data 9. Evaluation design 10. Alternatives not taken 11. Threats to validity 12. References

1. The claim under test

An AI tutor that is given classroom context organised around a shared curriculum map produces better tutoring turns than the same tutor given the same context as raw records, or no context. "Better" is operationalised as five judged criteria (§9). The map is the independent variable; the tutor model, its system prompt, the pupil's evidence and the teacher's materials are held constant across arms.

The prototype does not test whether pupils learn more. It tests whether the tutor's first reply is more appropriate to a known pupil and class. That is a necessary condition for the stronger claim, not the claim itself.

2. Component architecture

Four data layers are kept in separate tables and never merged. The separation is the central architectural decision: each layer has a different owner, a different rate of change and a different truth condition.

LayerTablesNatureChanges when
Reference graphnode, edge, crosswalkGoverned, versioned. Nodes are never deleted: a retired node is marked deprecated with a replaced_by pointerA curriculum release
AlignmentsalignmentDerived, probabilistic. Every row carries a confidence, a provenance (which tagger) and the graph version it was made againstContent is ingested or re-tagged; a release migrates them
Evidenceevidence, behaviour_eventAppend-only. Records what a pupil did, its source, and how its topic IDs were obtainedA pupil does something
Learner statelearner_state, learner_misconception, learner_indicator, learner_constructA projection: rebuilt in full from the evidence log by replaying it through the current graphEvery time evidence is added, and at a release

Two services sit over these layers. The alignment service (§4) turns free text into graph IDs. The context assembler (§7) joins the four layers into one briefing per tutoring turn. The tutor itself is a thin client: a fixed system prompt plus whatever context object it is handed. It is exposed through MCP and REST so that any tutor can consume the briefing without a bespoke integration.

The release demo (maths map 2026.2 → 2026.3) exists to show the layering doing work: two concept nodes are merged, alignments are migrated to the new ID and re-stamped, evidence is left untouched, and learner state is rebuilt. Evidence recorded against the old IDs still resolves because the projector follows replaced_by chains.

Federation. The store is single-tenant, but its identifiers are designed for federation. Every topic has a deterministic UUID (uuid5 of its readable alias) and a resolvable URI, exported read-only in CASE v1.1 form [R2]. Cross-scheme links are held as typed mappings using the SKOS mapping vocabulary (exactMatch, closeMatch, broadMatch) [R1], so two organisations can keep their own IDs and publish how they correspond. CASE itself only distinguishes exactMatchOf from isRelatedTo; the finer SKOS match types are preserved in the map and noted in the export.

3. The map as an ontology

The map is a lightweight domain ontology rather than a formal one: a fixed set of node types and typed, directed relations, with no axioms or reasoning beyond graph traversal. In Noy and McGuinness's terms [R3] it is a taxonomy of concepts plus a small set of relations chosen for the competency questions the tutor needs answered: what must be secure before this?, what error pattern explains this answer?, how does this teacher teach this?, what has this class reached?

Node typeRelationsUsed to answer
ConceptprerequisiteOf (weighted), relatesTo (undirected)Readiness, learning edge, next step
Misconceptionaffects → conceptCredit assignment for wrong answers; diagnosis
Method, Representationteaches → conceptConsistency with the teacher's practice
Quotation (English)evidences → concept; inSection → actWhich parts of the text a topic can be discussed from
Section / act (English)orderedScope: how far the class has read

Two shapes. The maths map is a partial order: 23 concepts with weighted prerequisites, and a learning edge defined as the earliest taught concept (by prerequisite depth, then week) that the pupil has not secured. The English map is a web: 35 topics in five strands, where only the writing-skills strand carries prerequisites and the rest are joined by relatesTo. The knowledge-space view of a curriculum as a prerequisite structure over which learning states are defined [R4] fits the maths map directly; it does not fit the English map, and the prototype's handling of that difference (§7) is where most of the design effort went after the maths results.

What the map deliberately excludes. Learning objectives, mark schemes, difficulty levels and lesson sequences are not nodes. Difficulty is a property of an item and a pupil, not of a concept; sequence belongs to a class's scheme of work, which is school data, not curriculum. Keeping these out is what lets two classes teach the same map in different orders and with different methods.

Authoring process. The two shipped maps were authored by one person without review. The process by which a defensible map would be produced (scope, document draft, specialist authoring, independent review, tagging trial with an inter-rater agreement test, versioned release), the structural validator that every map must pass, and a worked example are on the Authoring page.

Granularity. Concept grain was set by hand at "one thing a teacher would set a lesson on" for maths and "one thing an essay paragraph would be about" for English. This is a judgement, not a derivation. Data-driven refinement of the grain, such as Learning Factors Analysis [R5], would need far more evidence than the prototype holds.

4. Alignment: mapping text to the graph

Everything that enters the system as text (a worksheet unit, a markbook activity title, a pupil message) is aligned to graph IDs by one service with two interchangeable implementations and a single output contract: up to three concepts, at most one method, at most one representation, up to three misconceptions, each with a confidence in [0, 1].

  • Keyword tagger. Each node carries a vocabulary of keywords. Matches are scored with phrase bonuses and inverse document frequency across the node set; the score is squashed to a confidence by 1 − e−s/1.5. Deterministic, no model, and used as the fallback.
  • Graph-constrained model tagger. Claude is shown the candidate node list (all concepts when the subject has ≤ 60, otherwise the keyword-ranked top 30), the full misconception, method and representation lists with descriptions, and rules that distinguish "mainly about" from "uses along the way". It returns JSON. Every returned ID is validated against the graph and the subject; anything not on the map is rejected and reported. The model chooses among a closed set; it cannot invent a topic.
  • Deterministic text references (English). Act numbers, named events and key quotations are matched by string rules, not by the model, because they are facts about the text rather than judgements about it.

The tagger prompt was tuned once, against a 14-unit practice set, after which two further maths sets and one English set were written and locked before being run (unseen, or held-out, sets). The three sets are reported separately on the Evaluate page because their numbers mean different things (§9).

5. Learner model

The learner model is a per-concept mastery estimate with graph propagation, deliberately simpler than the standard alternatives so that its behaviour can be read off the code.

  • Update rule. Each concept holds a mastery m ∈ [0, 1], initialised at 0.5. An observation with outcome o moves it by k(o − m), where k = b·w / (1 + 0.12·n): b is 0.4 for an item answer and 0.6 for a teacher's mark; w is 1.0 for evidence tagged at source or by a teacher and 0.6 × confidence for evidence tagged by the alignment service; n is the number of direct observations so far. This is an Elo-style estimator with a decaying step size, in the family Pelánek describes for adaptive systems [R6], chosen over Bayesian Knowledge Tracing [R7] because it needs no per-concept parameter fitting and handles graded marks as well as binary outcomes. Its known weakness is that a single strong teacher mark only reaches "developing" (thresholds: secure ≥ 0.7, developing ≥ 0.4).
  • Prerequisite propagation. A success adds weak evidence to each prerequisite: mp += 0.15 · strength · w · (1 − mp), counted as inferred rather than direct. A failure propagates nothing, because a failure on a composite skill does not identify which component failed.
  • Graph-based credit assignment. When a wrong answer matches a known distractor, or a teacher records a misconception, only the concepts that misconception affects are marked down. A pupil who bolts context onto a good analysis is marked down on the context skill, not on the character they wrote about.
  • Misconception strength. Incremented by 0.3·w per diagnosis (capped at 1), multiplied by 0.7 on each later success on an affected concept, and treated as active at ≥ 0.5. Misconceptions therefore fade with counter-evidence rather than persisting as labels.
  • Rebuild, never patch. The whole state is recomputed from the evidence log on each change. This costs little at prototype scale and guarantees that a graph release changes the projection without touching the evidence.

The parameters (0.4, 0.6, 0.12, 0.15, 0.3, 0.7, and the thresholds) were set by hand so that the synthetic scenarios produce the states they were written to produce. They have not been fitted to data and should not be read as estimates.

6. Learning-behaviour layer

A second, smaller framework records how a pupil works rather than what they know. It is kept separate from the curriculum map because its constructs are cross-curricular, but every observation is still recorded against a topic on the map, because a behaviour only means something relative to what the pupil already knows. The pipeline is three-level and rule-based: observed events per answer → indicators per episode → construct patterns per pupil.

  • Constructs (six): planning, monitoring and checking, self-assessment accuracy, persistence after difficulty, help-seeking, adapting strategy. They are drawn from the self-regulated-learning literature, in particular the Winne and Hadwin model of studying as a monitored, adaptive process [R8]. The help-seeking indicators follow Aleven et al.'s distinction between help sought after an attempt and help used in place of one [R9].
  • Knowledge-aware rules. A hint requested before any attempt counts against help-seeking only if the topic is one the pupil is already secure on or the class was taught before the current week. On a new topic, early help is reasonable and is not counted.
  • Patterns are recent, not traits. A construct's score is (Σw₊ − Σw₋)/(Σw₊ + Σw₋) with episode weight 0.85k for the k-th most recent episode. "Pattern to support" needs at least two negative indicators carrying ≥ 50 % of the weight; "strength" needs at least two positive indicators and ≤ 20 % negative weight. Fewer than two indicators is "too little evidence".
  • Governance. Affect signals (e.g. frustration) are discarded at ingestion and never stored. Only teacher-confirmed patterns are exposed beyond the tutoring tool. The tutor is instructed to adapt how it helps and never to describe the pupil with a label.

The indicator rules are hand-written and unvalidated. Detecting behaviours such as gaming or disengagement from interaction logs is an established research area with trained detectors; this layer is an interface design for such signals, not a detector.

7. Context assembly

One call produces the briefing for one turn. Its logic is deterministic given the graph, the learner state and the class coverage; the only model call is an optional reading of the pupil's message (intent and named topic), which has a rule-based fallback.

  1. Read the message. Classify intent (specific, check_answer, practice, revision, next, harder, start, stuck, explain_method, other) and the topic it names, if any. The topic must be a valid, active concept of the pupil's subject.
  2. Compute scope. Maths: a concept is taught once a dated, taught lesson is aligned to it at confidence ≥ 0.5. English: the writing-skills strand is always in scope; any other topic is in scope if a taught lesson names it, or unless every quotation evidencing it sits in an act the class has not reached. Acts are ordered, so reaching act n implies acts 1…n.
  3. Find the learning edge. Maths: earliest taught concept, by prerequisite depth then week, that is not secure or is affected by an active misconception. English: topics affected by an active misconception first, then gaps, then developing topics.
  4. Choose the focus. A topic named in a specific question wins; a named topic beyond the taught scope becomes a flagged preview; otherwise the learning edge; otherwise a weak prerequisite of taught work; otherwise the latest taught topic.
  5. Choose the next step. Readiness-aware: consolidate if the focus is not secure; else the next dependent in the class's scheme; else, in a web subject, use this topic to practise the learning edge, or connect to a related topic the class has studied. A request for a part of the text not yet reached becomes "answer briefly, say it is coming up, link back".
  6. Retrieve materials. Hybrid: filter the teacher's units to those aligned to the focus, then rank by a hashed bag-of-words cosine with additive boosts for method match (+0.5) and misconception coverage (+1.0). The raw-records condition uses cosine only. The embedding is a 512-dimensional feature hash of unigrams and bigrams, chosen to avoid a model dependency; it is not a semantic embedding.
  7. Assemble. Focus, pupil state on it, relevant misconceptions (including, in English, misconceptions about cross-cutting skills whatever the focus), prerequisites, class scope, key quotations from studied acts, materials, the "how to support" briefing, and guidance: diagnosis, teach with, avoid, check first, next step, scope rule.

This is retrieval-augmented generation in the sense of Lewis et al. [R10], but with the retrieval driven by graph structure rather than by similarity alone. The comparison between the "raw records" and "map" conditions is precisely a comparison between similarity-only and graph-structured retrieval over the same corpus.

8. Construction of the synthetic data

No real pupil, teacher or school data is used anywhere. Every fixture was written by hand against the map, and each was designed to make one thing visible.

  • Item bank (maths). 16 items, each tagged at source to one or two concepts, with a correct answer and distractors. Each distractor that corresponds to a known error is tagged to the misconception it reveals. This is the mechanism by which a wrong answer becomes a diagnosis rather than a mark.
  • Pupils. Nine maths, five English. Each has a scripted scenario of five to eight events chosen to produce a specific state: one active misconception, or a prerequisite gap, or secure on everything, or a behaviour pattern. Two maths pupils (Isla, Jay) give identical answers and differ only in process events, to test whether the behaviour layer changes the tutor's reply.
  • Classes. Two per subject, in the same week of the same scheme, taught with different methods: balance versus "change side, change sign" in maths; thesis-first with zoom-in versus PETAL in English. The pairing isolates method sensitivity.
  • Materials. Dated, week-numbered teaching units written in each teacher's voice, some marked planned (a future week). Coverage, "taught so far", and the teacher's preferred method are all derived from these by alignment, never declared. That is the point: the map has to recover the scheme from the materials.
  • English evidence. Teacher-marked written work: a task, the topics the teacher says it covered, a mark, and optionally a misconception. There is no item bank, because literature has no distractors.

Synthetic data is a limitation as well as a control. The scenarios were written by the same person who wrote the briefing logic, and the raw-records condition receives unusually clean records (a teacher's comment per piece of work, exact quiz titles). Both effects are discussed in §11.

9. Evaluation design

Two things are measured: the alignment service, and the effect of the briefing on the tutor's reply.

Alignment accuracy

Each test unit has hand-written gold: expected concepts, additionally acceptable concepts, method, representation and misconceptions. Concept precision counts a tag correct if expected or acceptable; recall counts expected only. Off-topic units (a poem, a language-paper task) must receive no concept tags. The sets are: a 14-unit practice set used to adjust the prompt; two maths unseen sets and one English set, written after the last prompt change and never used to alter anything.

Tutor A/B/C

Each scenario is a pupil, a message, and hand-written ground truth: the pupil's actual need and a good next step, plus per-class ground truth on method, taught content and content not yet taught. The tutor answers three times with the same system prompt and different context objects. These three are the conditions of the test (in trial terminology, the arms; the API and export files use arm as the field name):

Condition (each reply is generated once per condition)Context the tutor receives
NonePupil's name and year only
Raw classroom dataLast eight evidence rows as text (source, activity, mark, teacher's comment), plus the three most similar units by text cosine
Organised by the mapThe assembled briefing (§7)

Each reply is scored on five criteria from 0 to 3 by a model acting as judge, with the ground truth and rubric in the prompt and the reply quoted verbatim: diagnosis (addresses this pupil's actual need), method (consistent with this teacher), scope (respects what has and has not been taught), next step (right for this pupil now), grounding (claims about pupil and class are true; a fabricated fact scores 0). The behaviour suite adds a sixth, support. Two independent judge passes are averaged. Model-as-judge with a rubric and reference is the protocol studied by Zheng et al. [R11], who report high agreement with human raters for pairwise and graded judgements but also position bias and verbosity bias; the design here mitigates the first by scoring each reply alone, and does nothing about the second.

Tutor as a variable

The tutor is an adapter with one method, respond(context, message, subject) → reply. Three implementations exist: the built-in stub; a webhook that receives each turn as JSON and returns a reply; and an offline exchange in which every turn (scenario × condition, with its context) is exported, answered elsewhere, and the replies uploaded. All three are scored by the same judge against the same ground truth, and results are stored per (suite, tutor) so tutors can be compared on one set. This turns the evaluation from "does the map help this stub?" into "does the map help tutor T?", which is the question a vendor or school actually has. The caveat in §11 about the judge encoding one pedagogy applies with more force when tutors differ from each other than when one tutor is compared with and without the map.

Unseen-set discipline

Every fix was made on one set and then scored on an unseen set (a held-out set, in machine-learning terms) written and committed before the fix existed. The Evaluate page shows the before-fix score alongside each result. Two runs of the same suite differ by around ±1 point in 15, so differences inside that band are reported as noise.

What was found

Across four suites (maths development and unseen; English first and unseen) the map condition beat the raw-records condition by 1.5 to 3.7 points in 15, and beat the no-context condition by 5 to 8. The gains concentrate in scope (not teaching ahead of the class), method (using the teacher's approach) and grounding (fewer invented facts); diagnosis is where the raw-records condition is closest, because a teacher's comment on each piece of work is itself a diagnosis. One failure mode recurred in both subjects: when a pupil names what they want, the focus logic can override it with the pupil's weakest skill.

The KLI framework [R13] is the natural theoretical home for the next design question: which kinds of knowledge component (fact, procedure, principle) each map node represents, and therefore which instructional move (retrieval practice, worked example, contrasting cases) the briefing should recommend. The prototype's "method" nodes are a coarse stand-in for that.

11. Threats to validity

  • Author bias. One person wrote the map, the scenarios, the ground truth and the briefing logic. Unseen sets were written before each fix, but by the same author with the same mental model.
  • Generous raw-records condition. The raw records are cleaner than real markbooks: every piece of work carries a teacher's comment naming the error. This favours that condition on diagnosis and makes the map's margin conservative on that criterion, but that condition also never has to deal with noise.
  • Model as judge. The judge and the tutor are the same model family. The rubric and ground truth constrain it, and two passes are averaged, but self-preference and verbosity biases are documented [R11] and unmeasured here.
  • Small n. Ten to fourteen scenarios per suite, five to nine pupils. The ±1 run-to-run band is an observation from repeated runs, not a confidence interval.
  • Hand-set parameters. Every constant in §5 and §6 was chosen to make the scenarios come out as designed. None has been fitted or validated.
  • Two subjects, one text. Transfer from a ladder to a web has been shown for one play. A subject with neither structure (design and technology, say) is untested.
  • Scope inference from materials. Coverage is inferred from tagged worksheets. A class whose materials do not mention an act is assumed not to have read it. A real deployment would take the reading schedule as an input.

Authoring

How to make a curriculum map for a new subject

The two maps in this prototype were written by one author from general subject knowledge, with no expert review and no data. That is acceptable for a proof of concept and not for anything a school would rely on. This page sets out a repeatable process that ends in a defensible map, gives you the file template and a structural checker, and walks through one small unit from start to finish.

What a map contains

A map has five kinds of content. They come from different places and are judged by different people, so “make a map” is really five tasks.

ContentWhat it isBest sourceWho can judge it
Concepts, at the right grainThe topics, sized at one lesson's worth (maths) or one paragraph's worth (English)The specification and the national curriculum, broken down by subject specialistsSubject specialists, examiners
StructurePrerequisites (a ladder) or related-topic links (a web); strands; parts of a set textSpecialists' judgement, later checked against dataSpecialists first; learner data later
MisconceptionsNamed, recurring error patterns, each tied to the topics they show up inExaminer reports, marking, item-bank distractors, subject-education researchExaminers, experienced teachers

CrosswalksLinks to other schemes: DfE content, assessment objectives, a shared layerMechanical from the specification, then reviewedAssessment and standards teams

Two things follow. The specification is the natural spine: it exists, it is governed, and it is what teachers teach to. And misconceptions and methods are the valuable, hard part. They do not come from documents; they come from people who mark and teach.

Required inputs

  • A scope decision. One qualification, one unit or theme. Both prototype maps cover about one unit; that is the right size for a first version.
  • A shape decision. Ladder (layers: topics build on each other) or web (strands: topics connect sideways and can be met in any order). Decide before drafting, because it changes what “structure” means and what the tutor does with it.
  • The governing documents. The specification or programme of study; assessment objectives; any scheme of work you want the map to serve.
  • Error evidence. Examiner reports for the unit; a sample of marked work; if an item bank exists, its distractors and what each one reveals.
  • Teaching evidence. Two or more schemes of work or textbooks that teach the unit differently, so the methods list is plural.
  • People. Two or three subject specialists to author; one reviewer who did not author; access to a class's real materials for the trial.

The process, in six stages

  1. Scope. Fix the unit and the shape. Write one sentence on what a pupil who is “secure on this unit” can do; it becomes the test for what belongs.
  2. Draft from documents. Break the specification into candidate concepts; pull assessment objectives into crosswalks; harvest misconceptions from examiner reports and distractors. A language model can do this first pass quickly and consistently. That produces a draft, not a map.
  3. Specialist authoring. Two or three specialists decide grain, fix the structure, write the misconception descriptions (what the pupil does and why), name the methods, and add keywords in the words teachers actually use. Record a one-line rationale for every non-obvious decision in the file's authoring block.
  4. Review. A separate reviewer works through the checklist below. Disagreements are logged with a status (resolved, deferred, accepted), not averaged away.
  5. Trial against real material. Load the map, tag a body of real teaching materials and, if possible, a sample of marked work, and look at what the tagger does: unmatched materials, suspicious tags, concepts that never fire, concepts that always fire together. Fix keywords and grain accordingly. Then have two people tag the same twelve units independently and compare: that agreement figure is the best single measure of whether the grain is right.
  6. Release and revise. Give it a version. Every later change is a new version; retired concepts point to their replacements rather than disappearing, so evidence recorded against old versions still counts. Publish the CASE export so others can map to it.

Validating a map: three kinds of check

Structural (automatic)

The map is a graph, so some faults are simply testable. The checker below refuses a map with any of these: prerequisites that form a cycle; a reference to a concept that is not defined; a misconception that affects nothing, or a method that teaches nothing; a concept with fewer than three keywords, or without a label; a crosswalk with an unknown match type; an id with capitals or spaces. It warns about things an author should look at: a concept with no links at all; keywords shared between concepts; most concepts having no misconception or method attached. Both prototype maps pass it. Passing the checker means the map is well-formed. It says nothing about whether the map is right.

Expert (judgement)

The reviewer's checklist below covers what cannot be automated: whether each concept is a real unit of teaching, whether each prerequisite is a genuine dependency or just the usual order, whether each misconception is a pattern with a cause. The agreement test in stage 5 turns one of these judgements into a number.

Empirical (data)

Once the map has been used against real evidence, its structure can be checked against outcomes. Do pupils who fail a prerequisite fail the dependent topic more often than those who pass it? If not, the link is doubtful. Does a diagnosed misconception predict later errors on the topics it supposedly affects? Are there concepts that are never tagged, or always tagged together (a sign they should merge)? These checks need volumes of data the prototype does not have. They are the difference between a credible map and a validated one, and the methods for them are cited on the Theory page.

Check a map file

Paste a map (the YAML format used by the template) or choose a file. The checker runs the structural checks and reports errors and warnings with the line they refer to. Nothing is stored.

Worked example: KS3 fractions, adding and subtracting

A small unit (seven concepts, six lessons) authored end to end, chosen because it is not in either prototype map and because fraction errors are well documented. The full file is downloadable below and loads into the checker; here is what each stage produced.

Stage 1: scope

Year 7, one unit. Shape: ladder. Secure means: “can add and subtract any two fractions or mixed numbers, and apply it in a worded problem.”

Stage 2: draft from documents

The KS3 programme of study gives one line: use the four operations applied to proper and improper fractions and mixed numbers. Examiner reports for Foundation Paper 1 name three recurring errors. That is the whole documentary input; it yields perhaps three concepts and three misconceptions.

Stage 3: specialist authoring

The specialists split the one line into five lesson-sized concepts and added two the specification assumes but does not list, equivalent fractions and lowest common multiple, because the department's marking (about 90 scripts) shows that is where the errors originate. Three decisions were recorded:

  • “Add with the same denominator” kept separate from “add with different denominators”, because pupils secure on one are often not secure on the other. Grain follows the evidence, not the specification's sentence structure.
  • LCM → common denominator weighted 0.6 rather than 1.0: any common multiple works; the LCM is efficient, not necessary. Weights encode how hard a dependency is, not how usual.
  • The “butterfly” cross-multiplication shortcut is listed as a method even though the subject lead disapproves of it. The map records what is taught, not what should be; the briefing will steer away from it for classes that don't use it.

Stage 4: review

The reviewer (a head of maths who did not author) logged three findings: one resolved (a misconception was attached to the wrong concept; it originates in equivalence, so it was attached to both), one deferred (comparing and ordering fractions is missing, but out of scope for this unit), and one accepted (the keyword “same denominator” is shared by two concepts; it genuinely belongs to both, so it stays, with a note to watch it in the trial).

Stage 5: trial

Eighteen units from two departments' schemes were tagged. Two were correctly left untagged (a decimals starter, a cover sheet). One suspicious tag: the butterfly method fired on a bar-model worksheet that said “cross out”, because the keyword “cross multiply” was too close. The keyword was tightened. Two people then tagged the same twelve units: ten identical, two differed where the worksheet mixed same- and different-denominator work. Grain judged acceptable.

Stage 6: release

Version 2026.1. The structural checker passes with one warning, the shared keyword the reviewer already accepted. Total specialist time: about nine hours of authoring, two of review.

The example's trial and review figures are illustrative: they describe what the process produces, using plausible numbers, because no real trial has been run on this map. Everything else in the file (concepts, links, misconceptions, methods) is a genuine authoring attempt at the unit.

Reviewer's checklist

For the person who did not write the map. Answer each in writing; a “no” is a logged finding, not a veto.

  1. Is every concept something you would recognise as a unit of teaching? Could you set a lesson, or a paragraph, on it and nothing else?
  2. Take twelve real worksheets. Would you and the author put each on the same concept? Count the disagreements.
  3. For each prerequisite: is this a genuine dependency (a pupil who lacks the first cannot do the second), or just the usual order of teaching?
  4. For each misconception: is it a recurring pattern with an explanation, or a mistake? Does its description say what the pupil does and why? Is it attached to every concept it actually shows up in?
  5. Are the methods a fair range, including ones you would not choose yourself?
  6. Read the keywords aloud. Are they how teachers in your department actually write and speak about this? Which words would you add?
  7. Teach one lesson from the map in your head. What did you need that is not here?
  8. Is anything here that a pupil at this stage would never meet, or that belongs to a different unit?

Effort and tooling

For one GCSE or KS3 unit with an existing specification: the document draft takes hours; specialist authoring one to two weeks of two people's part-time effort; review and trial about another week. Almost all of the cost is people. The tooling that helps most, in order:

  1. The structural checker (on this page), so nothing malformed reaches a review.
  2. An authoring format specialists can edit without touching YAML. The template is the first step; a spreadsheet version with import is the obvious next one.
  3. A tagging-trial report: unmatched materials, low-confidence tags, concepts that never fire. The Teacher's materials page shows the pieces; a single report would save the reviewer assembling them.
  4. An agreement test that gives two reviewers the same sample and scores their agreement.

What none of this replaces: the empirical checks against real pupil data (see “Validating a map”). Those need a map in use at scale, and they are what would let the process claim a map is validated rather than credible.

CASE export (1EdTech CASE v1.1, read-only)

        
Every topic has a permanent CASE identifier (a UUID derived from its readable ID, so it never changes) and a web address that resolves to its description. The readable ID, such as cc:maths/alg/lin-eq-both-sides, is kept as humanCodingScheme. The map, the MCP tools and the API accept any of the three forms.

        

        

          
/ims/case/v1p1/CFDocumentsThe frameworks: one per subject

          
/ims/case/v1p1/CFPackages/{id}A whole framework: topics, groupings and links

          
/ims/case/v1p1/CFItems/{id}One topic. This is the address its identifier resolves to

          
/ims/case/v1p1/CFItemAssociations/{id}One topic with all its links

        

        
What maps to CASE: topics, strands and acts become CFItems; prerequisites become precedes; related topics and close or broad crosswalks become isRelatedTo; exact crosswalks become exactMatchOf; retired topics become replacedBy. What stays in the map: misconceptions, teaching methods, representations and quotations. CASE has no native types for these, so they remain the publisher's teaching layer and point at the CASE addresses. Crosswalk targets use placeholder urn: addresses until those schemes are published in CASE.
